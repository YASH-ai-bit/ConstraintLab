# ConstraintLab

> An agent-native job-shop scheduling workspace built around WebMCP, one canonical application state, and a deterministic HiGHS MILP solver.

ConstraintLab is a browser-based factory scheduling environment where a human and an AI agent collaborate on the same optimization model. The human expresses operational intent and evaluates trade-offs. The agent converts that intent into typed, validated WebMCP tool calls. A real mathematical optimizer—not the language model—computes the schedule.

The project intentionally focuses on one complete, inspectable loop:

1. Read the current scheduling model.
2. Add or update typed constraints.
3. Solve the exact model in a Web Worker with HiGHS.
4. Inspect the resulting Gantt chart or deterministic infeasibility facts.
5. Review every action in a versioned audit timeline.

**Private hosted build:** [constraintlab-factory-scheduling.y62193312.chatgpt.site](https://constraintlab-factory-scheduling.y62193312.chatgpt.site) (owner sign-in required)

## Why this project exists

Agent-enabled applications often expose a second, simplified state model to an agent or let a language model produce an answer that merely looks valid. ConstraintLab takes the opposite approach:

- The UI and WebMCP tools call the same domain actions.
- The agent cannot bypass validation by constructing raw solver expressions.
- Every structural mutation increments the same `modelVersion`.
- The solver receives an immutable snapshot of that exact model.
- A solution is readable only while its `solvedModelVersion` matches the current model.
- Infeasibility explanations are computed from typed constraints, not generated by an LLM.

The central invariant is:

```text
                         ┌─────────────────────┐
React UI ───────────────▶│                     │
                         │  Domain actions     │
WebMCP tool handlers ───▶│  (validation +      │
                         │   mutation boundary)│
                         └──────────┬──────────┘
                                    │
                                    ▼
                         Canonical Zustand state
                         ├─ modelVersion
                         ├─ jobs / resources
                         ├─ typed constraints
                         ├─ solve state
                         └─ immutable audit events
                                    │
                                    ▼ immutable snapshot
                         LP compiler → HiGHS worker
                                    │
                                    ▼
                         onSolverResult domain action
```

There is no `agentUpdateJob`, agent-only model, UI-only draft, or solver-owned application state.

## WebMCP integration

ConstraintLab uses the imperative WebMCP API on the top-level document:

```ts
await document.modelContext.registerTool(toolDefinition, {
  signal: registrationAbortController.signal,
});
```

Registration is feature-detected at startup. When a native `document.modelContext` is not present, the application loads [`@mcp-b/global`](https://www.npmjs.com/package/@mcp-b/global), which installs the compatible fallback surface. If both paths fail, the application records and displays an explicit `unavailable` status while leaving the complete human workflow operational.

Each registration has:

- a stable tool name;
- a human-readable title and explicit `readOnlyHint` / `untrustedContentHint` annotations;
- a task-oriented description written for agent discovery;
- JSON Schema generated from the same Zod schema used at execution time;
- an `execute` handler returning one MCP text content block;
- a serialized `ToolSuccess<T>` or `ToolFailure` response envelope;
- timing and success metadata recorded in the developer panel.

Registrations are attached to an `AbortController`, allowing a subsequent registration pass to retire the previous set cleanly without maintaining a second tool registry.

Long-running `solve_problem` calls also honor the WebMCP execution `AbortSignal`. Cancellation terminates the dedicated worker, restores the prior solve state when the model has not changed, writes a structured audit event, and returns `SOLVE_CANCELLED` rather than leaving the workspace in `SOLVING`.

### Tool surface

ConstraintLab registers exactly nine tools.

| Tool | Class | Input | State effect |
| --- | --- | --- | --- |
| `get_problem_state` | Read | `{}` | Returns the compact canonical model, versions, solve status, and stale flag. No mutation. |
| `add_job` | Write | Validated job fields | Calls the shared `addJob()` domain action. |
| `update_job` | Write | `{ id, updates }` | Calls `updateJob()` with an explicit field allowlist. |
| `add_constraint` | Write | One discriminated typed constraint | Calls `addConstraint()`; raw algebra and custom types are rejected. |
| `remove_constraint` | Write | `{ id }` | Removes one stable-ID application constraint through `removeConstraint()`. |
| `set_objective` | Write | `{ type: "makespan" }` | Calls the shared `setObjective()` action. |
| `solve_problem` | Compute | `{}` | Snapshots the current model, runs HiGHS in a worker, and commits through `onSolverResult()`. |
| `get_solution` | Read | `{}` | Returns assignments only when the solution version is current. |
| `analyze_infeasibility` | Read | `{}` | Runs deterministic typed conflict checkers after an infeasible solve. |

Authoritative definitions live in:

- [`src/webmcp/toolDefinitions.ts`](src/webmcp/toolDefinitions.ts)
- [`src/webmcp/schemas.ts`](src/webmcp/schemas.ts)
- [`src/webmcp/toolHandlers.ts`](src/webmcp/toolHandlers.ts)
- [`src/webmcp/registerTools.ts`](src/webmcp/registerTools.ts)

### Response contract

Every application-level tool result uses one of two envelopes:

```ts
type ToolSuccess<T> = {
  ok: true;
  data: T;
};

type ToolFailure = {
  ok: false;
  code: string;
  message: string;
  recoverable: boolean;
  suggestedAction?: string;
};
```

Failures are intended to be actionable by an agent. Examples include `VALIDATION_ERROR`, `UNKNOWN_JOB`, `UNKNOWN_RESOURCE`, `UNKNOWN_CONSTRAINT`, `PRECEDENCE_CYCLE`, `SOLVE_IN_PROGRESS`, `NO_SOLUTION`, and `STALE_SOLUTION`.

### Validation boundary

Inputs are validated twice by design:

1. The WebMCP handler parses the agent-supplied arguments with Zod.
2. The shared domain action validates again before changing state.

The second check is the correctness boundary. Tool schemas improve discovery and error quality, but the application never treats an agent's arguments as trusted merely because they arrived through WebMCP.

Read-only tools operate on cloned or compact snapshots. Tests assert that they do not change model data, version counters, or audit history.

### Recommended agent procedure

An agent should follow this sequence:

```text
get_problem_state
        │
        ├─ use returned stable IDs
        ▼
add_constraint / update_job / add_job
        │
        ▼
solve_problem
        │
        ├─ optimal or feasible ──▶ get_solution
        │
        └─ infeasible ──────────▶ analyze_infeasibility
```

The agent should not cache IDs across resets and should call `get_problem_state` again after unexpected validation or reference errors.

## Canonical state and model versioning

The Zustand vanilla store in [`src/state/store.ts`](src/state/store.ts) is the single application state container. React subscribes to it through a thin hook, while WebMCP handlers call `appStore.getState()` directly.

Structural actions increment `modelVersion`:

- add or update a job;
- add, remove, enable, or disable a constraint;
- change the objective.

Every solver result records the version of the immutable snapshot it solved as `solvedModelVersion`.

```ts
const staleSolution =
  solvedModelVersion !== undefined &&
  solvedModelVersion !== modelVersion;
```

When the model changes after a solve:

- the UI displays **Model changed — re-solve required**;
- the previous chart remains visibly marked as out of date;
- `get_problem_state` returns `staleSolution: true`;
- `get_solution` returns `STALE_SOLUTION` instead of stale assignments.

This is also the primary synchronization mechanism demonstrated between human and agent interaction: either actor can mutate the model, and the next reader observes the same version immediately.

## Domain model

Time values are integer minutes after midnight. For example, `720` is 12:00 PM and `780` is 1:00 PM.

### Job

```ts
type Job = {
  id: string;
  name: string;
  durationMinutes: number;
  priority: number;
  earliestStart?: number;
  deadline?: number;
  requiredResource?: string;
  predecessors: string[];
  lockedStart?: number;
  lockedResource?: string;
};
```

### Resource

```ts
type Resource = {
  id: string;
  name: string;
  availableFrom: number;
  availableUntil: number;
  unavailableWindows: { start: number; end: number }[];
};
```

### Typed application constraints

Constraints are first-class application objects with stable IDs. They are not anonymous solver rows.

| Type | Parameters | MILP meaning |
| --- | --- | --- |
| `precedence` | `predecessorId`, `successorId` | Successor starts after predecessor completion. |
| `resource_assignment` | `jobId`, `resourceId` | The selected job must use the selected resource. |
| `resource_availability` | `resourceId`, `start`, `end` | Jobs on the resource must run entirely before or after the downtime window. |
| `deadline` | `jobId`, `deadline` | Job completion cannot exceed the deadline. |
| `earliest_start` | `jobId`, `earliestStart` | Job start cannot precede the bound. |
| `locked_start` | `jobId`, `start` | Job start is fixed to an exact time. |

There is deliberately no `custom` type and no tool that accepts raw LP syntax. This keeps constraints discoverable, auditable, structurally explainable, and safe to compile.

The only objective implemented in this build is:

```ts
type OptimizationObjective = { type: "makespan" };
```

## Deterministic solver pipeline

ConstraintLab uses [`highs`](https://www.npmjs.com/package/highs), the WebAssembly build of the HiGHS optimization solver.

```text
OptimizationProblem snapshot
        │
        ▼
modelCompiler.ts
        │  emits CPLEX LP-format text
        ▼
solver.worker.ts
        │  loads highs.wasm off the main thread
        ▼
highsAdapter.ts
        │  reads Status, ObjectiveValue, and Columns[*].Primal
        ▼
solutionTranslator.ts
        │  maps encoded variables back to job/resource assignments
        ▼
onSolverResult()
```

### MILP formulation

For each job `j` and resource `r`, the compiler creates:

- continuous start variable `s_j`;
- binary assignment variable `a_jr`;
- pairwise binary order variables for jobs that may share a resource;
- binary before/after variables for resource downtime windows;
- continuous makespan variable `cmax`.

The objective is:

```text
minimize cmax
```

Subject to the following families of constraints:

```text
cmax ≥ s_j + duration_j                         for every job j

Σ_r a_jr = 1                                   exactly one resource per job

s_successor ≥ s_predecessor + duration_predecessor

s_j + duration_j ≤ deadline_j

s_j ≥ earliest_start_j

s_j = locked_start_j
```

Resource non-overlap and downtime avoidance use standard disjunctive big-M constraints. The compiler emits explicit CPLEX `.lp` text because the JavaScript HiGHS package consumes LP text rather than a JSON model.

Solver execution is configured for reproducibility:

- presolve enabled;
- MIP relative gap `0`;
- random seed `0`;
- 30-second time limit;
- solver console output disabled.

An `Optimal` result is translated to exact assignments. A valid incumbent returned at a supported limit status is surfaced as `FEASIBLE`. Infeasible status invokes the deterministic conflict analyzer. Other statuses become an explicit solver error.

The worker never imports or mutates React state. It receives a structured-cloned problem snapshot and posts a `SolverResult`; only `onSolverResult()` commits that result to the canonical store.

## Deterministic infeasibility analysis

ConstraintLab does not ask the language model to explain why a schedule failed, and it does not depend on a MILP IIS implementation.

[`src/solver/infeasibility.ts`](src/solver/infeasibility.ts) evaluates the typed model using deterministic checks for:

- mutually exclusive resource assignments;
- precedence chains that force completion beyond a deadline;
- locked starts that violate deadlines;
- locked intervals that overlap resource downtime;
- assigned jobs whose duration cannot fit in any contiguous resource window before their effective deadline;
- earliest-start and precedence-derived lower bounds.

A conflict contains machine-readable references and a computed human-readable fact:

```ts
type Conflict = {
  constraintIds: string[];
  jobIds: string[];
  resourceIds: string[];
  summary: string;
};
```

The browser agent may restate these facts conversationally, but it is not the source of the facts.

The analyzer is deliberately bounded. If HiGHS proves the MILP infeasible but no supported local rule isolates the cause, it returns an explicit “no typed local conflict isolated” result instead of inventing an explanation.

## Exact demo scenario

The included Factory Scheduling scenario contains 15 jobs, four machines, resource assignments, machine availability, and precedence chains. It is feasible and solves optimally before additional constraints are introduced.

### Prompt 1: constrained but feasible

Ask a WebMCP-capable agent:

> Use ConstraintLab’s site tools. First inspect the current problem state. Optimize the schedule. Machine 2 will be unavailable between 1 PM and 3 PM, and Job 7 is urgent—it must finish before noon. Add the constraints, solve the problem, and inspect the solution.

Expected tool sequence:

```text
get_problem_state({})

add_constraint({
  "id": "m2-downtime",
  "type": "resource_availability",
  "parameters": {
    "resourceId": "machine-2",
    "start": 780,
    "end": 900
  }
})

add_constraint({
  "id": "job7-deadline",
  "type": "deadline",
  "parameters": {
    "jobId": "job-7",
    "deadline": 720
  }
})

solve_problem({})
get_solution({})
```

Expected result: HiGHS returns an optimal schedule and Job 7 completes no later than 12:00 PM.

### Prompt 2: proven infeasible

Then ask:

> Also force Job 4 onto Machine 2 and make it finish by 12:30. Solve again. If it is infeasible, call `analyze_infeasibility` and explain the returned deterministic conflicts.

Expected additional calls:

```text
add_constraint({
  "id": "job4-machine2",
  "type": "resource_assignment",
  "parameters": {
    "jobId": "job-4",
    "resourceId": "machine-2"
  }
})

add_constraint({
  "id": "job4-deadline",
  "type": "deadline",
  "parameters": {
    "jobId": "job-4",
    "deadline": 750
  }
})

solve_problem({})
analyze_infeasibility({})
```

Expected result: the MILP is infeasible. The analyzer identifies Job 4, Machine 2, the assignment constraint, and the 12:30 PM deadline. Job 4 needs 240 contiguous minutes, but Machine 2 opens at 9:00 AM, leaving only 210 minutes before 12:30 PM.

This two-prompt sequence is encoded as an integration test and runs twice to guard against accidental state leakage or one-shot demo behavior.

## Auditability and developer diagnostics

Every structural action produces an immutable `AuditEvent` containing:

- actor: `human`, `agent`, `solver`, or `system`;
- timestamp and event summary;
- `modelVersionBefore` and `modelVersionAfter`;
- structured input and output snapshots.

The audit timeline exposes actions and results, not hidden reasoning or chain-of-thought.

The collapsible developer panel shows:

- native, polyfill, checking, or unavailable WebMCP status;
- the exact registered tool list;
- recent tool call durations and success state;
- an explicit assurance that the human workflow remains operational when WebMCP is unavailable.

## Testing strategy

The minimum correctness bar is enforced at five layers.

| Test area | What is verified |
| --- | --- |
| Domain actions | Job creation/update, invalid references, precedence-cycle rejection, downtime and deadline constraint creation, and version increments. |
| Solver/compiler | Explicit LP text, binary variable families, solution translation, and hand-verifiable one-machine schedules. |
| Infeasibility | A known contradiction returns `infeasible` with matching typed constraint facts. |
| WebMCP handlers | Unknown IDs, invalid deadlines, stale-solution rejection, and read-only non-mutation. |
| End-to-end demo | The exact two-prompt sequence produces an optimal first solve and genuine second-solve infeasibility, twice. |

```bash
npm run test
npm run build
```

## Design decisions

### Why WebMCP instead of DOM automation?

Scheduling mutations have domain semantics that are difficult to infer safely from visual controls. WebMCP gives the agent narrow operations, validated IDs, typed arguments, recoverable failures, and deterministic output while the human keeps the visual workspace.

### Why keep constraints as application objects?

Stable, typed constraints can be discovered by agents, selected in the UI, recorded in audit events, compiled into solver rows, and referenced in conflicts. Solver-only constraints would break that traceability.

### Why compile LP text explicitly?

The `highs` package accepts CPLEX LP-format text. Keeping compilation in a dedicated module makes the mathematical model inspectable and independently testable instead of hiding it in UI or worker glue.

### Why run the solver in a worker?

The HiGHS WebAssembly payload and MIP solve must not block interaction or animation on the main thread. The worker also enforces a clean architectural boundary: model snapshot in, `SolverResult` out.

### Why rule-based conflict explanations?

The demo needs correct facts, stable constraint references, and predictable latency. Typed local checkers provide those properties and avoid presenting generated prose as a proof of infeasibility.

## Intentional scope

This is a focused hackathon build, not a general-purpose optimization IDE.

Implemented:

- one Factory Scheduling scenario;
- one `makespan` objective;
- six typed constraint families;
- exactly nine WebMCP tools;
- human and agent mutation paths;
- deterministic MILP solving and typed conflict analysis;
- one current solution with explicit stale-version handling.

Intentionally not implemented:

- multiple objectives;
- raw/custom constraints;
- batch model patches;
- assignment lock/unlock tools;
- saved-solution comparison;
- checkpoints;
- drag-to-reschedule;
- additional demo scenarios;
- persistence across refresh.

These omissions keep the shared-state, solve, inspect, and iterate loop small enough to be verified end to end.

## Review checklist

For a WebMCP-oriented review, the critical files and behaviors are:

1. Confirm the nine tool descriptors in `toolDefinitions.ts` are specific and discoverable.
2. Confirm their JSON Schemas are generated from strict discriminated Zod schemas.
3. Trace a write handler from `toolHandlers.ts` into the same action used by React in `store.ts`.
4. Verify read tools do not mutate state and stale solutions are rejected.
5. Inspect the LP compiler independently from the worker and UI.
6. Run the exact demo test and verify that infeasibility facts contain stable constraint IDs.
7. Disable or remove native WebMCP and confirm the fallback/unavailable state does not break the human workflow.

ConstraintLab's success criterion is simple: the agent may help construct the model, but only validated domain actions may change it, and only the deterministic solver may decide the schedule.
